# Where Cargo first accepted an ambiguous method call

Cargo PR #53 introduced the conditional metadata code. Its default configuration waited for the provider in this four-crate workspace. The same held for the head of PR #55. PR #54 enabled the compiler and Cargo settings that allow the middle crate to commit its unchanged public API before the provider publishes its changed metadata. That was the first default configuration in this stack that returned success for the edited and repeated invalid check. An independent empty check reported E0034. Four later Cargo revisions from the histories of PRs #71 and #101 exhibited the same failure.

The source fix for PR #53 is `613667eadce39c044ec1cf4327a985619de636f7`. The merge into the original defaults branch for PR #54 is `aa935f6f696f1281a98ccbad2403ca4bb5df3892`. Each branch has its corresponding patch here. The corrected #54 reported the same diagnostic bytes on edit, repeat and empty build in both publication orders. Both branches recovered after restoring valid Rust. Their 57 and 65 fingerprint unit tests passed, including the pending-dependency case.

The exact original order attempt timed out on #53 and #55 when the provider was held. The initial receipts stop after the edited command in each instance. Two separately named controls preserve that timeout and follow the resulting ordinary order through the repeat, empty compile and restoration. Ordinary checks without the interposer returned the correct diagnostic even on the original #54 in this run. The stale result requires a possible scheduling order. These experiments use the unmodified released Linux -18 rustc with historical Cargo's own defaults.

Run `python3 -IB verify.py` here. To replay the ordered case on a private SDK, run `python3 -IB historical-reproduce.py /path/to/sdk /tmp/new-empty-run provider-late --expect correct`. The original #54 expects `stale` for that order. Use a new output directory for each run.
