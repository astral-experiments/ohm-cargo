# Reuse of Cargo’s lockfile encoding during cache publication

A normal `cargo +ohm build -p ruff_text_size --locked --offline` serialized the workspace resolution once when reversing the historical Ruff edit, and once when restoring it. The matched control serialized twice in each direction. Both products still opened, shared-locked and read the full 138,994-byte lockfile four times on each transition. The next unchanged build on each version read the file once and serialized zero times. This untimed comparison covers one selected production library in Ruff’s 553-package lockfile. [Control and original mechanism receipts](../rc20-workspace-lockfile-double-decode/) · [Historical Ruff edit](https://github.com/astral-sh/ruff/commit/6dc1031889aa24a0461457409d39861e279242a9)

The candidate keeps the writer's final canonical encoding until it can compare it with the newly locked file at cache publication. Cargo accepts line-equivalent text and hashes the exact bytes it just read. If the lines differ, the existing serializer runs with the new contents, including any preserved header comments. The implementation leaves the earlier two typed lockfile reads in place. `candidate.patch` is the complete source change against `9d675d9393b5ff1ecebe764d1a554f8fd64175ef`, including a regression test for a valid noncanonical `--locked` file.

A separate process obtained a nonblocking exclusive `flock` in all five synchronized cases. It either replaced the lockfile inode with malformed TOML, changed the existing file to a same-length stale version, or added the header comment. The verifier checks that each previously opened Cargo descriptor had released its lock and closed before the change. It reconstructs every consumed byte from its own generation and verifies the full strings observed at the writer and fallback returns. Four data mutations exercise the verifier’s refusal paths.
