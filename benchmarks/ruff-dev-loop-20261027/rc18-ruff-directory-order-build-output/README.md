# The Ruff build script observes filesystem enumeration order

A validation build reported 548 of 619 workspace artifacts fresh after moving a byte-identical, timestamp-preserving source copy to another filesystem. The settled baseline reported 563. Cargo's implicit package watch selected `Cargo.toml` or `build.rs` as the first file at the same maximum modification time. Both records have exactly `1792012558.000000000s` and the same build-script dependency identity. Fifteen extra artifacts became dirty. The active generated ZIP changed in that run. [Cargo path fingerprint](https://github.com/astral-sh/ohm-cargo/blob/7caf39914da1e28a67744ecbc963a5f26361474d/src/sources/path/mod.rs#L1013)

Ruff's original build script walks `vendor/typeshed` and writes each entry to the ZIP in the order returned by the filesystem. On the primary machine the 1,565,618-byte ZIP changed from `fe924018…` to `82e3e4b7…`. Its first member changed from `source_commit.txt` to `LICENSE`. All 819 member names and their uncompressed payloads matched. Placing the identical package on storage with the donor's full directory order reproduced the original ZIP. A second 5,577,690-byte ZIP from a different build-unit profile happened to stay unchanged during this particular workspace transition. [Ruff ZIP writer](https://github.com/astral-sh/ruff/blob/93526150df078af7dd8fc4226cdcc469539d2001/crates/ty_vendored/build.rs#L57)

An independent machine ran the verified stock-built Ruff script on three physical filesystems using the same 772 tracked source files, including the file modes and all file and directory mtimes. Two invocations on each filesystem reproduced its exact output. The three 5,577,690-byte ZIPs had different bytes and identical decompressed member payloads. Relative to the first output, 810 and 812 of 819 member positions differed on the other two filesystems. Consumers using `include_bytes!` can observe the full generated ZIP.

## Shipped worktree behavior

Stock Linux Ohm 1.99.0-18 created two actual Git worktrees with `cargo +ohm worktree add`. Each imported 83 files including 80 physical copy-on-write clones. The fixture's build script writes its observed directory order into the compiled program. Both recipient directories enumerated files differently from their donors. The first checkout used normal Git checkout timestamps. The second reproduced all 38 tracked donor mtimes exactly. In both cases the recipient reran the build script once, and the program printed its own file order. Each warm recipient executable matched an independent, empty-target, empty-shared build byte for byte. Each following unchanged command reused the correct result.

An initial test fixture inherited root's home during privilege drop and failed to launch Cargo. Its successor selected the ordinary user's proxy explicitly. A first private SDK installation exceeded the harness timeout. The completed install used the same verified release assets and installer in another private prefix. Both source filesystems rejected a direct copy-on-write ioctl, so the confirmed imports used a separate, private Btrfs output filesystem. Cargo and its test programs ran with the normal unprivileged UID and full UID mapping.

Run `python3 -IB verify.py` and `sha256sum -c SHA256SUMS` in this directory. To repeat the seeded comparison, run `python3 worktree-replay.py --work-root /new/source-and-logs --other-source-root /other-fs/new-source --cow-root /reflink-fs/new-output --rustup-home /path/to/verified-rustup --cargo-shim /path/to/rustup/cargo`. Use fresh output directories, a released `ohm` alias, Git, strace and a Rustup Cargo proxy. A second execution of this exact runner reproduced both 80-reflink imports, all four changed-order verdicts across the two runs, and the byte-for-byte clean executable matches. The evidence supports keeping the build-script rerun when the directory order changes. Each downstream artifact still requires its own dependency check.
