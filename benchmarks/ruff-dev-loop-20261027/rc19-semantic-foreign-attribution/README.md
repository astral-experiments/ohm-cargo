# Foreign spans in the historical ty_python_semantic workload

Four unconditional `salsa::Update` derives in `ty_python_semantic` provide a concrete source path to rustc’s foreign `Span::join` marker. Qualified Cargo 235f922 and the release -18 compiler a4fa11bc ran 16 full semantic compilers over 12 unchanged commands. These were the first and second repeats in both directions of the 716260bf → 2d6ce561 selection edit, separately for check, native build and native test. Each compiler has its own argv digest and matching missing `ohm-foreign-span-bytes` in the retained stderr. The target records identify the compiler mode, chosen externs, the Salsa macro artifact and the actual `proc_macro2` build-script cfgs. The historical exec records stop at the process boundary. They do not count bridge calls or identify additional operations or macros. ## What the evidence permits

The emitted bit merges five possible operations. Span Debug can expose global byte offsets or a non-root hygiene context, including for a locally written token. Byte range checks either endpoint, join checks the imported file after file IDs agree, subspan marks imported input before testing bounds, and source text marks the imported source before attempting a snippet. An untrackable imported source sets an additional bit and produces a different sentinel. A subsequent Debug can short-circuit its test once another operation set the shared bit. The binary's direct `--extern *.so` list cannot identify every macro since crates can reexport procedural macros. [Bridge implementation](https://github.com/astral-sh/ohm-rust/blob/a4fa11bcd38280639cb94daacc125472657db6c3/compiler/rustc_expand/src/proc_macro_server.rs#L712)

Cargo #254 used checksums obtained by reopening paths and could mark the observer input set complete. An ordinary changed input could give the compiler 17, later give the checksumming step 29 and leave a supposedly fresh 17 executable while an empty build produced 29. Cargo #261 keeps the missing marker even for an authenticated old complete record. Rust #244 reruns native procedural macros on a compile. #233, #238 and #245 address interface reachability, replayed hygiene and metadata's exported source coordinates. None of these supplies the identity of all inputs at the point a particular native macro consumed them, or makes its returned span invisible. The four Salsa source paths establish no safe fresh-build exception. ## Minimum physical attribution

One untimed, isolated replay of the exact semantic library argv and pinned prerequisites would test the source prediction for that mode. Record the active expansion identity (`macro_def_id`, crate and derive/attribute name), resolved macro DSO identity, and each of the five eligible bridge operations with predicate status, stable source-file IDs, source-relative endpoints, syntax contexts and result (including None). Tie distinct joined spans to returned token spellings, especially `__binding_0`. Inspect Debug even after the first store, since an atomic watchpoint alone sees only the first transition. Keep the ordinary compiler's input/argv and final dep-info beside the diagnostic run. Repeat separately for the other three argv identities before claiming all four unit kinds are covered. Compare outputs and diagnostics to ordinary runs. This measurement would identify the callers and operations on that path. A future freshness proof would additionally have to cover the consumer-visible generated spans, code that actually ran, and relevant source, artifact and external bytes as consumed, including replacement races.
