# Does #233 avoid compiles after three other Ruff parser edits?

The first native timing study compared Ohm Rust #233 with its parent on a t-string diagnostic edit. This study compares those same two release compilers on three different historical edits, holding the FIFO-safe Cargo #254 and bundled Wild fixed. The three workloads were originally selected for a separate two-compiler optimization. All three are included here. That optimization had already been tried on `cargo build` before this comparison was designed. [Original timing study](https://github.com/astral-sh/ohm-cargo/tree/2f07518331735487c84aaeadab58ce98d7c5a71b/benchmarks/ruff-dev-loop-20261027/native-qualified-results) · [Original three-edit selection](https://github.com/astral-sh/ohm-cargo/tree/7ef4e84e3838cabd8e713fcadef6347a67f9fc00/benchmarks/ruff-dev-loop-20261027/first-occurrence-parser-plan)

Each source edit and restoration gets a physical process trace, a complete Cargo output roster, checks of the resulting Ruff program, and a subsequent fresh command. Both original compiler arms start from empty stores, with separate cold states for build and test-build. The entire historical patches are applied in a private Ruff worktree view. The signed-pattern edit removes two real historical test fixtures, and the resulting Ruff executable must stop issuing the two expected syntax errors until restoration.

The outcomes are numbers of compiler and linker processes and observable behavior for these exact edits. This comparison does not use traced elapsed times to estimate speed. `plan.json` fixes the source revisions, binary hashes, edit ordering, disk gates, runtime inputs and outcome checks before first exposure to the two compilers being compared.
