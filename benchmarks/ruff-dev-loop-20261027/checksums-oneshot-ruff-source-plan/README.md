# Checksum verification on small Ruff source files

The source patch applies to Cargo #262 at `105fe8286bef83e1ad1b62b3a2c015a6ace57ee7`. It changes only the BLAKE3 branch in `Checksum::compute`. A short first read is copied into a bounded prefix. Cargo makes a second read on the same source with the original full buffer. If that read returns EOF, the one-shot library routine hashes the complete prefix. If it returns more data, the incremental path consumes the prefix, that second read and all subsequent bytes. A full first buffer takes the incremental path directly. The first EOF on an empty stream uses the existing incremental empty digest. All reads propagate errors as before. The SHA-256 branch, descriptor opening, metadata checks, cache and checksum format are unchanged.

One allocation and a prefix copy are part of this candidate's cost. A reusable second 64 KiB buffer could avoid that copy but would add per-worker storage and change how the shared checksum routines receive scratch space. This screen selects the single-file implementation and includes its copy. There is no performance result in this packet.

## Functional checks

The fixture extracts the exact two checksum methods and the SHA-256 adapter from the product tree. The local development Ohm compiler built one release-optimized binary with the locked BLAKE3 1.8.5 and SHA-2 0.11.0 crates. A native comparison verified 5,200 combinations of buffer capacity, read width, errors and EOF boundaries across both algorithms, plus 96 real-file cases covering growth and shrinkage after reading initial metadata and during reads of the same open descriptor. Both implementations also passed a reader requiring fixed-size requests, and each generated the same BLAKE3 and SHA-256 result for all 1,238 pinned Ruff files. BLAKE3 was cross-checked against an independent C library, and SHA-256 against Python's implementation.

The rejected first sketch read into the unfilled part of the buffer after a short read. Linux packet pipes exposed the error on a real file descriptor. A one-byte first packet followed by a 64-byte second packet delivers all 65 bytes to the original 64-byte requests. A 63-byte second request discards one byte. The corrected implementation yields the original digest on this test. See `rejected-first-slice/packet-v1.stdout` and `packet-v2.stdout`.

The real corpus covers 12,381,544 bytes from the 268-unit linter trace, including the reverse of the historical one-byte documentation edit. The three generated input paths from that command cannot be reconstructed from Ruff Git objects and are excluded. Of the source-controlled files, 1,215 are smaller than 64 KiB, and 1,090 are larger than one BLAKE3 chunk while still fitting the buffer. The helper's read-and-hash loop omits Cargo's graph and preparation work. [Original released-Cargo attribution](https://github.com/astral-sh/ohm-cargo/tree/ec9be8521d899553d94402fbeab7cbd394e6e347/benchmarks/ruff-dev-loop-20261027/settled-cargo-depfile-instruction-results/support/profile)

Run `python3 -B verify.py` to check the archived evidence. To reconstruct inputs, use `python3 recreate-corpus.py --ruff /path/to/pinned/ruff --out /new/corpus`. With an isolated Cargo home and target, `cargo +ohm build --release --locked --offline` in `fixture/` rebuilds the standalone harness from the locked libraries. Its `check /new/corpus /empty/scratch` action exercises the functional cases. The prospective screen requires separate fixed host and counter bindings, another native read audit and explicit admission.
