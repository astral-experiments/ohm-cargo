# An ordinary caller requires the current parser credential

On Linux x86-64, reverse Ruff `6e29838d4b` against `93526150df`. The H2 study retained the edited producer and its restoration as native `ruff_python_parser.rmeta` artifacts. A real externally exposed item moved from lexer.rs line 1623 to 1620. The two ordinary callers in this experiment use different Ruff interfaces: `ruff_python_codegen::Mode` or `ruff_python_importer::Insertion`. The former workspace library received a direct parser `--extern`. The latter recorded the parser transitively. Both have no recorded incremental node keyed to the moved function; the replayed libraries' local metadata query recorded the parser's whole public hash. These observations do not establish that all possible position observations have been recorded.

The unmodified libraries carry the original parser dependency hash, `2c88767d4708e7ef4666d0b611edaa86` in rustc’s displayed byte order (crate numbers 20 and 101). The edited native parser exposes `d341df56c87d0f07f5084e2bf9eb3d6b`. Its private hash is also different. The ordinary caller resolves exactly the same library file, dependency search path, and logical crate names in both runs. On the matched restored parser both callers compile. On the edited parser both fail E0460, and each loader trace identifies the expected and actual hashes. The only Rust search directory that contains a parser was replaced with a private read-only directory containing solely the selected parser `.rmeta`. The 231 other Rust search directories were left untouched, along with both native search paths. Explicit root reexports of `ruff_python_parser::lexer::lex` compile in both states; the erroneous zero-argument caller reports the actual declaration note at 1623:8 vs 1620:8.

The controlled 18 rustc invocations used an exact distribution-profile writer/reader (`7c31057e`), and independently the #233 distribution-profile reader (`dec72d1e`). H2 native library inputs were originally generated by the former. The latter independently loaded the same matched original graph before being tried on the changed one. An unchanged `ruff_python_codegen` was then fully compiled using its genuine historical native rustc argv, fresh private output, the edited parser, and the first reader. Its new metadata records the edited parser credential; the same new ordinary Rust caller now compiles. A preliminary Rust-2024 path-only caller without `extern crate` emitted less-specific E0463 on the stale library; the explicit ordinary extern forms expose the actual E0460 cause.

`complete.json` under `observations` records raw on-wire little-endian SVHs, physical input/output hashes, and trace hashes. Each subdirectory contains the actual argv, success/error code and diagnostic bytes. The native recompile redirected outputs and disabled incremental storage, so the rebuilt intermediary's own private/public identities or minor `.rmeta` byte differences cannot be attributed solely to the one parser change. No claimed performance difference, no changes to either tool.

A cached auxiliary semantic hash, or absence of per-definition query keys, cannot authorize reusing these two byte-identical historical library artifacts with the current locator. The producer metadata must still expose present definition locations. A sound future design would have to validate a replacement dependency contract in the emitted library and in rustc’s loader. The existing graph is not a certificate covering warning emission, diagnostics, generated spans, proc macros or other untracked readers. Existing origin-sensitive controls include a real proc macro observing a foreign byte position, a reexported foreign diagnostic, and dependency-provided deprecation warnings. The seven earlier candidate terminals do not emit Rust library metadata, but the existing native-dependency admission rule accepts none of them. This experiment claims zero skipped compiles.
