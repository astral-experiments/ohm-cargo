# Where Rust reads an observer's inputs

The release and experimental first-observer captures both write dep-info after expansion. A checksum can attest the bytes consumed only if the compiler has retained an immutable view of those bytes, or can otherwise prove that a later observation describes that same generation.

| Input | Acquisition on 337a07a79 | Consequence |
| --- | --- | --- |
| Local Rust text | `rustc_span::SourceFile::new` calculates the source hash, optional checksum, and original length before normalizing the text. | A parsed source with an authenticated original checksum can use that value. A reopened filename must never overwrite it. Without a raw checksum, only provably unnormalized retained text can supply one. |
| `include_str!` and `include_bytes!` | `source_util::load_binary_file` receives the actual byte buffer and also records the path in `Session::file_depinfo`. `SourceMap::load_binary_file` substitutes empty text for non-UTF-8. Source files are deduplicated by stable filename. | Record or compare the original byte buffers at each acquisition, or decline when the raw generation is unavailable. Two different acquisitions of the same pathname cannot produce one complete checksum. Explicit checksums presently replace the original SourceMap value with a freshly computed one. |
| Macro `tracked::path` | `proc_macro_server::track_path` gets a pathname from an arbitrary macro. The macro manages its own I/O. | Reading the path earlier or later does not attest its file access. The experimental guard uses the existing untrackable marker for an observing crate. |
| Foreign `Span::source_text` | `SourceFile::add_external_src` confirms the original physical source hash before normalizing, then caches either the text or a failed import. The dep-info writer only retains the path. | Memory of the verified bytes or failure at the operation is essential. A later open can produce a checksum for different bytes or availability. The two-guard experiment declines this case. |
| Standalone `.rmeta` | The locator opens and mmaps the whole file. CStore holds the mapped byte slice. | Hashing the retained mapping would distinguish an atomic rename from a different path generation. The private-mapping control shows a same-inode in-place write changes that mapping. A transient edit can also disappear from pre/post digest checks. |
| Rust archive or dylib metadata | `DefaultMetadataLoader` maps the archive or dylib and returns an owned slice of its metadata member. CStore records additional located binary paths. | The metadata slice by itself does not attest an entire archive, separately selected native member, or actual host instructions. The existing Cargo protocol expects whole-file input checksums. |
| Native proc-macro dylib | `host_dylib` canonicalizes a path, opens it with the platform loader, obtains a symbol and intentionally leaks the library. The metadata loader operated separately. | DSO contents and metadata are different acquisitions. The real equal-metadata/different-native-code witness requires the loaded code generation. Simply loading a sealed copy by a new filename changes observable `dladdr` and can break a genuine `$ORIGIN` dependency. |

Comparable reasoning is required for a selected codegen backend, PGO input and debugger visualizer before a complete opaque protocol certifies their bytes. Neither small marker experiment supplies such a general certificate. On normal `ron`, the 45 inputs include one host proc-macro dylib; preserving its cutoff in a partial experiment does not resolve the DSO case.

The private-mapping experiment concerns Linux filesystem behavior and records that ctime advanced in its in-place cases. It does not assert how an implementation using stronger, enforced filesystem generation contracts would behave. The synchronized ordinary Cargo source-text experiment and the release repair are separate end-to-end proofs.
