# Why two guarded compiles slowed a Ruff workspace build

On a real Ruff parser change, the experimental Cargo ran one full compiler, two guarded compilers, six link-only compilers and eight Wild links. Its control ran three full compilers, six link-only compilers and the same eight links. The registered workspace build medians were 5.617 s and 6.385 s. The guarded Cargo was 14.03% slower across paired builds (95% interval 8.63% to 20.05%, Holm p=.000252). The test-build result was inconclusive. [Registered paired comparison](https://github.com/astral-sh/ohm-cargo/tree/722ba0fde16c048b2df47ba2649461d5f60cb715/benchmarks/ruff-dev-loop-20261027/mixed-alloc-cargo-wall-storage-plan-v2) · [Native and external Rust caller qualification](https://github.com/astral-sh/ohm-cargo/tree/0cc0537dde525ffd62c6fd090bb836ccb044c661/benchmarks/ruff-dev-loop-20261027/mixed-alloc-same-compiler-qualification-results)

The independent build diagnostics here identify two passes over the mixed libraries’ transitive artifacts. During one complete successful edit, Cargo read 3,417,849,932 bytes from the 752 identified inputs. The control read 418,654 bytes from the same path list. The experiment grouped individual thread reads by Linux thread-group ownership and retained the full syscall records. These are bytes returned by the kernel, including page-cache hits.

| Actual Cargo read on the edit | Control | Guarded Cargo |
| --- | ---: | ---: |
| Transitive inputs | 418,654 B | 3,417,849,932 B |
| Rlib bytes among those inputs | 0 B | 2,033,093,232 B |
| Rmeta bytes among those inputs | 0 B | 868,030,494 B |
| Existing .rlink bytes, all units | 924,549 B | 5,473,113 B |
| Saved codegen objects, all units | 12,912,552 B | 39,062,408 B |
| All successful reads | 85,496,908 B | 3,538,868,792 B |

Neither Cargo returned any bytes through the traced copy_file_range or sendfile syscalls. The Wild processes requested the same total mapped length of 3,700,774,550 bytes from identified inputs in both arms. An mmap length records neither page faults nor physical device traffic.

The ruff_wasm recipe listed 671 files (795,020,110 bytes), and ty_wasm listed 674 (920,753,379 bytes). They shared 593 files containing 527,395,461 bytes. Cargo checked 1,701,661,125 bytes before the compilers, then read another 1,715,770,153 bytes after them. Its six other native links could already run during validation. The last ty_wasm artifact could only finish after the second read.

In Cargo source 190d261a8546f121e3aa1adf237d85e02164eb18, RelinkCachePaths::native_library_recipe calls fingerprint::native_library_changes before rustc. It authenticates fresh and early-cutoff inputs with a content hash. A producer rebuilt in the same invocation must supply the expected native interface. After successful rustc execution, RelinkCachePaths::initialize calls Fingerprint::native_library_inputs. That method reads and hashes the whole transitive output set again, including outputs just verified. The cached-file reader uses BLAKE3. These reads are in Cargo’s two job threads, independently of the real GCC and Wild child processes.

In three further edit/restore cycles on the same guarded Cargo, Linux task children associated each job thread with its actual rustc PID. The central 98% of the last ty_wasm read pass had a median duration bracket of **0.533 to 0.563 s**. Even its entire median rustc-exit-to-artifact interval, including other Cargo work, was 0.628 to 0.643 s. Four of the six entire intervals had upper bounds under the original 0.768 s difference in medians. Two slow intervals reached 0.89 s and 0.95 s. Each ruff_wasm pass took 0.27 to 0.33 s for its central 98% and ran alongside other native jobs. The two upstream checks still took 0.60–0.63 s and 0.66–0.68 s, respectively. Both ran concurrently. Adding their durations would overstate elapsed time. A prior independent edit on the original incremental storage measured a 0.315–0.344 s central read for ty_wasm.

Keeping the last full compile’s authenticated receipt could remove the second 1.716 GB pass on a confirmed hit. A later changed input presented as fresh must still cause a fallback if its digest no longer matches that retained receipt. The new output, fallback generation and interruption semantics would also have to stay intact. The fixed-schedule direct opportunity is smaller than the registered median regression in most of the observed commands. These diagnostics cannot put a bound on indirect gains from reduced contention. This study leaves the original slow candidate unqualified and makes no performance claim for a proposed revision.

## Reading the evidence

The immutable inputs are Ruff 93526150df078af7dd8fc4226cdcc469539d2001 and the full historical parser edit 3ea20f6161cbf59cb56595dfb634ec24bfa82f0b in both directions. B and C shared rustc driver SHA-256 63145e253973980f3786ce562b2342d2590b4a783256e4197e8ffacdf7d110fa. All diagnostic commands used the real Cargo shim, a separate native lock, the registered 24-CPU affinity and eight jobs. The diagnostic runs had compiler info logging and Cargo JSON enabled. Their elapsed times are outside all performance inference.

- `registered-comparison.json` preserves all preceding build and test wall rows separately.
- `input-receipts.json` lists actual recipe digests, sizes and suffix classes in both modes. Only the build was instrumented here.
- `successful-reads.json.gz` gives the successful reads, ordered-phase attribution and path-blinded per-input counts. `successful-read-classes.json` separates Rlib, Rmeta, Rust codegen objects, recipes, native DSOs and other files. Path identifiers are SHA-256 of complete original paths.
- `exact-exec.json.gz` records actual exec, exit and SIGCHLD times, roles, output names, and sampled resource counters. `ptrace-control.json.gz` retains the heavier trace from both directions. Ptrace substantially perturbed the validation duration, even in the separately requested filtered mode. Use these files for process structure and operation ordering. Each of eight distinct native output links could also fork a worker under the same executable name.
- `nonptrace-timelines.json.gz` uses only observed process samples and output arrival clocks. It includes four build directions across the two arms. The external process sampler ran on a separate CPU. Observed sampling gaps are retained, and interval endpoints express sampling resolution.
- `per-worker-observations.json.gz` contains six separate candidate commands and their per-TID byte and CPU samples. Each checked rustc must appear as that worker’s child. Successive cumulative rchar samples bound the 1% and 99% crossings relative to that child’s disappearance. The numerical thresholds use the traced postscan bytes per library. Per-task rchar covers other reads as well. It supplies a window around the known work, rather than tagging each of those reads with a source function. The Rust incremental cache alone was mounted from the secondary ext4 device for these six commands. The measured .rlib/.rmeta, native output and recipe paths stayed on their original device. `first-physical-worker-edit.json.gz` preserves the initial independent edit with the original incremental directory.
- `raw-file-inventory.json.gz` binds complete receipts, captured streams and observations by SHA. Every admitted command reproduced its arm’s output/diagnostic reference, followed by a 501/501 fresh ordinary Cargo command with zero Rust compilers and zero Wild links. All 15 emitted workspace ELFs were byte-equal to the corresponding historical arm and source state. The 922 seed artifact files were independently copied and checked for size, mode, timestamp and SHA-256. Direct callers are part of the linked original qualification.
- `attempts.json` records an excluded wrong-namespace pilot, a corrected reference selection and a later disk-floor stop. Its first completed worker edit is retained separately. A complete private frozen seed was used for the last six commands.

Run `python3 -B verify.py` to rehash the archive, recompute the per-input byte totals, rederive all twelve native worker intervals from their numerical samples, and check the process and product gates. The supplied probe/analysis scripts record their expected native input layout. No compiler products or private source paths are needed for the portable verification.
