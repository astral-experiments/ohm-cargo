# An unused Ruff profile edit makes Cargo decode and serialize the same lockfile twice

In an ordinary dev build of Ruff's text-size library, reversing three lines in the unused `[profile.fast-test]` and then restoring them each invalidated Cargo's workspace-resolution marker. Both transitions kept the single Rust library fresh and ran zero compilers or linkers. Cargo nevertheless decoded the entire 553-package lockfile twice, constructed two previous-resolution graphs, and serialized the newly resolved graph twice. A settled invocation decoded and converted the lockfile once and did not serialize it. These are actual native calls in the production-profile Cargo. Each successful read consumed the exact 138,994-byte original file under a real shared lock. Thus the two ordinary transition commands each read 555,976 bytes of `Cargo.lock`. The two typed decoder callers were the cache check and the ordinary registry resolution. The other reads service the prospective lockfile write and marker publication. These read counts do not measure processor time or show a speedup.

The two serializer callers returned to `resolve_to_string_orig` and `mark_workspace_resolve_fresh` at ELF offsets `a7a678` and `a6c2d1`. Each received the original lockfile, and a separate run captured both complete generated strings immediately after their calls returned. Each return on either quiescent transition matched all 138,994 original bytes. The two graph arguments had different addresses across that handoff. ## Concurrent writers

A second ordinary process successfully acquired an exclusive nonblocking file lock at each recorded gap. All four actions were restricted to the private checkout.

- **Between the cache and registry decodes**, an atomic replacement supplied malformed TOML after the first decode succeeded. The second decoder received the new 12 bytes and Cargo exited 101 with a parse error. A same-inode, same-length edit instead changed the local package's locked version. The second decoder saw that change, and Cargo exited 101 because the lockfile would need updating. Statically installing each bad input reproduced its diagnostic class. Restoring it made the unchanged library usable immediately.
- **After the write-side comparison and before marker publication**, a stale package version made the marker's independently locked read disagree with the generated string. Cargo kept the previous marker. The in-flight build finished successfully and the next build rejected the already-stale lockfile. A valid added header comment instead made the second serializer return a different 139,025-byte string. Cargo correctly published a marker for those bytes, and the next unchanged invocation reused it.

A candidate that retains an earlier parse must still acquire and inspect the second snapshot. Reusing a complete earlier `Resolve` also requires accounting for `build_path_deps`, which loads local manifests. Separately, the writer's canonical encoding is a potential positive witness for marker publication if the new independently locked snapshot matches under Cargo's existing line comparison. Changed snapshots still need the existing serializer. ## What was observed

The original 373/388-unit Ruff CLI target was no longer in temporary storage. This study used a genuinely empty private target and then its warmed one-unit `ruff_text_size` build at the identical Ruff revision 93526150df. The optional serde test graph had 19 planned units, exceeding the 12-unit cap. Its graph was recorded without compiling the tests. Every successful instrumented build separately compiled and ran a real consumer of the produced library, which reported start 17, end 29 and length 12. The rlib, rmeta and consumer ELF agreed byte-for-byte on every successful phase. Those standalone oracle compilers are excluded from Cargo's native counts.

The observer starts the Rustup command normally. It enables four x86 instruction breakpoints only after observing the enrolled Cargo inode and matching its executable mapping. Each pass selected four independently bound function entries or return sites. At the typed parse and serialize entry it copied the actual input slices from Cargo's stopped process; in the return pass it copied the complete returned string from the actual result slot. Syscall observations separately committed the full bytes read from each opened descriptor and the shared locks around them. The recorder followed child execs to distinguish real Cargo compile/link work. Five separate ordinary commands with only exec tracing corroborated the fresh rosters and products. The published observer and patches reconstruct the three source versions. Their PC offsets apply only to the exact Cargo in `subjects.json`.

The 12 decoder commands, five serializer-entry commands, five ordinary controls and eight serializer-return commands ran without a Cargo source patch. All original receipts were retained. An earlier closed experiment proposed a persistent parsed-lockfile cache. An existing lockfile change avoids decoding during a successful textual comparison, and another optimizes package-ID collision checking. Those mechanisms differ from these two measured call pairs.
